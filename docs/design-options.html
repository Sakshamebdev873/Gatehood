App structure

Two roles, one app.

expo-router route groups split the builder and buyer sides. On launch, the app reads the signed-in user's record and sends them to the right group, so a buyer can never land on a builder screen.

Buyer 4 screens

app/(auth)/join.tsx          invite code: invalid, used, expired
app/(buyer)/_layout.tsx      tabs: Home, Updates
app/(buyer)/index.tsx        my unit, progress, possession
app/(buyer)/updates/index.tsx feed, filters, 15 per page
app/(buyer)/updates/[id].tsx  notice, marks it read

Builder 6 screens

app/(auth)/builder.tsx        email + password
app/(builder)/index.tsx       joined by tower
app/(builder)/import.tsx      CSV, preview, create codes
app/(builder)/buyers.tsx      codes, joined or pending
app/(builder)/notices/new.tsx  all / towers / units, pin
app/(builder)/notices/[id].tsx read count, who hasn't read

Repository one repo, all TypeScript

app/           expo-router screens
src/
  theme/       gatehood tokens: colors, type, spacing
  lib/         firebase client, audience keys
  features/    feed, notices, invites, units
  components/  Card, NoticeRow, StateViews
backend/
  firestore.rules
  firestore.indexes.json
  scripts/seed.ts     towers, units, 50+ notices
  tests/rules.test.ts emulator tests
.env.example          no real keys committed

Data model Firestore

units/{unitId}      tower, number, config,
                    progressPct, possessionDate
invites/{code}      unitId, name, phone,
                    expiresAt, usedBy, usedAt
members/{uid}       role, unitId, tower
notices/{id}        title, body, pinned, createdAt,
                    audience: ["all" | "tower:A" |
                               "unit:A-1204"],
                    readCount, targetCount
notices/{id}/reads/{uid}  unitId, readAt

Tech stack

What it's built with, and why.

LayerChoiceReason
AppExpo, React Native, TypeScript (strict), expo-routerRequired by the brief.Reviewers can run it in Expo Go with a QR code, no native build.
Splash + loadingexpo-splash-screen, then an in-app loading screenThe native splash (logo on the theme colour) stays up until fonts load.Then the loading screen shows real steps while sign-in restores and the unit and feed load. Returning users go straight to the cached feed.
Data + authFirebase JS SDK: Firestore and AuthLive feed through onSnapshot.Builder signs in with email. Buyer gets an anonymous account linked to a unit by the invite code.
BackendFirestore security rules, indexes, and TypeScript scriptsFirestore is the server.Rules enforce who reads what, one-time codes, and +1 read counts. No paid plan, nothing extra to host.
Feed queryaudience array-contains-any, pinned then newest, limit 15One query for All. My tower and My unit use one key each.Paginate with startAfter on the last notice.
Read countsReceipt document plus increment(1) in one batchRules allow the +1 only when the receipt is new.So counts can't be faked or doubled. Who hasn't read = joined units in the audience minus receipts.
OfflineAsyncStorage copy of the last feed page, NetInfo bannerThe JS SDK only caches in memory on React Native.This keeps the last feed after the app restarts.
CSV importexpo-document-picker and papaparseThe builder previews rows, then the app writes units and invite codes in batches.
Seed + setuptsx backend/scripts/seed.ts with firebase-adminService-account file and .env are gitignored.The README walks through it. The Firebase emulator works too.

Your call

Two choices before I build.

1. Which look?

  1. Notice boardMY PICK
    Closest to gatehood.com, reads well for long notices.
  2. Forest night
    Most striking in the video, but heavy for daytime reading.
  3. Site ledger
    Plainest, fastest to build, least like their brand.

2. What does "TypeScript backend" mean here?

  1. Firestore is the backendMY PICK
    Rules, indexes, seed script and rule tests, all in TypeScript. One thing for reviewers to run.
  2. Add a Node + Express API in TypeScript
    Handles CSV import and code redemption on a server. More code to show, but reviewers must run and host a second service.
